## Lifecycle and architecture decisions

The existing controller/service/repository architecture remains intact. Constructor injection and record DTOs preserve API boundaries. A dedicated `IncidentEvaluator` runs after the health check and service status have been flushed, within the same transaction. If evaluation fails, the check/status/incident transaction rolls back together.

Default thresholds are 3 consecutive DOWN checks to open and 2 consecutive HEALTHY checks to resolve. Both are configured through `launchguard.incidents` properties, with validated bounds of 1–1000. Recovery progress is derived from persisted recent history rather than mutable in-memory counters, so a failure interrupts the recovery streak and restarts it naturally. The evaluator retrieves at most the applicable threshold's recent check projections, using the existing service/time index.

The service row is locked with `FOR NO KEY UPDATE` until commit. This serializes incident evaluation without conflicting with the parent-key locks acquired by check inserts. See [PostgreSQL row-lock semantics](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS). A partial unique index independently enforces at most one OPEN incident per service. A real two-transaction integration test persists two different checks before concurrent evaluation and verifies that both transactions complete with one OPEN incident.

Incidents capture the deployment current at opening evaluation, which can differ from the deployment a probe captured before an in-flight deployment registration. Later registrations never rewrite incident associations. Services without deployments work normally.

`startedAt` is the threshold-reaching check timestamp. `resolvedAt` is the final recovery check timestamp. OPEN DTOs have null `resolvedAt` and `durationSeconds`; resolved durations are truncated to whole seconds. Entity identity, deployment, start, reason, and creation fields are not updatable, and the only transition is OPEN → RESOLVED. A resolved incident rejects further resolution. There are no incident mutation endpoints.

Service detail and list responses include `hasOpenIncident`; the list obtains open service IDs in one query rather than an incident query per service. A HEALTHY service can still have an OPEN incident while awaiting its recovery threshold.

## V3 migration design

V1 and V2 are unchanged. V3 creates only `incidents` and its indexes:

- UUID identity, service reference, nullable deployment reference, status, trigger reason, and start/resolution/creation/update timestamps.
- Service foreign key with `ON DELETE CASCADE`, consistent with existing history deletion semantics.
- Deferred composite `(service_id, deployment_id)` foreign key enforcing deployment ownership. It permits service-history cascade deletion but rejects independent deletion of a referenced deployment; it never cascades deployment deletion into incident history.
- Lifecycle check constraint requiring OPEN incidents to have no resolution and RESOLVED incidents to have a resolution on or after their start.
- Partial unique `(service_id)` index for OPEN incidents.
- `(service_id, started_at DESC, id DESC)` index for newest-first history and opening-time window filtering.

There is no incident backfill or reassignment of existing history. A staged V1 → V2 → V3 database test preserved a legacy healthy check with latency 42 and null deployment, and preserved a V2 service's current deployment. V3 is transactional and forward-only; applied migrations must not be edited.

## Endpoints

| GET endpoint under `/api/services/{serviceId}` | Behavior                                                                                     |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `/incidents?page=0&size=20&status=OPEN`        | Newest first; optional OPEN/RESOLVED filter; maximum size 100; API-owned pagination metadata |
| `/incidents/{incidentId}`                      | Incident details; ownership enforced                                                         |
| `/incidents/current`                           | Current OPEN incident, or 204 with no body                                                   |
| `/incident-metrics?window=30d`                 | Database-side incident aggregation                                                           |

Incident metrics reuse `MetricsWindow`: `1h`, `24h`, `7d`, `30d`, and `all`, with default `30d`. Windows select incidents by opening timestamp, inclusive at the cutoff. Open incidents are excluded from average resolution time but included in longest incident duration using request time. Empty selections return zero counts and null durations. Invalid pagination/status/window values return structured 400 responses; missing services and wrong-service incidents return structured 404 responses.

## Limitations and git status

- Single-instance monitoring remains the supported deployment model; the probe guard is process-local.
- Incidents describe sampled health-check streaks, not continuous downtime. Confirmation time is not the first failure time.
- Thresholds are global; changing them affects the next evaluation of persisted history.
- No historical incident backfill, retention, external notifications, manual-resolution endpoint, frontend, authentication, integration, rollback, or AI functionality.
- Incident windows select opening time, not overlap with the requested period.
- Existing trusted-URL/SSRF and unpaginated timeline limitations remain documented in the README.
