## Architecture decisions

The backend's existing controller/service/repository structure, DTOs, SQL aggregation, HTTP probe, scheduler, deployment correlation, and transactional incident evaluator are unchanged. The new backend dependency is Spring Boot Actuator, exposing only health with details hidden. Its aggregate health includes the datasource.

Compose defines `postgres`, `launchguard`, `payment-service`, `order-service`, and `notification-service` on its default network. The backend's JDBC URL is `jdbc:postgresql://postgres:5432/launchguard`; registered demo URLs use service DNS names, never container-to-container localhost.

Backend startup uses PostgreSQL's `service_healthy` condition, following [Docker's documented startup-order mechanism](https://docs.docker.com/compose/how-tos/startup-order/). PostgreSQL's probe explicitly uses TCP loopback so its temporary initialization-only Unix-socket server does not satisfy readiness. Demos do not gate backend startup: an unavailable target is a monitored failure.

Four multi-stage Dockerfiles compile with Temurin Java 25 JDK and run with the smaller JRE image. Runtime users are `launchguard`, `payment`, `order`, and `notification`; all measured UIDs were **100**, not root. Application containers also set `no-new-privileges`. Maven downloads use a BuildKit cache; ignored local tools/caches and environment files are excluded from image contexts.

Each tiny demo is a separate Spring Boot process with constructor-injected configuration, an atomic failure flag, and an atomic delay. There is no shared runtime state or new business functionality. Delay is bounded to 1..30000ms. `recover` changes only failure mode; `normal` changes only delay. Restart resets both controls.

No Flyway migration was added or modified. Database queries/indexes remain as in V0.4. Direct SQL validation confirmed successful V1/V2/V3 migrations. No startup seeding or fabricated checks were introduced.

## Endpoints and scripts

Backend addition:

- `GET /actuator/health`: container/database health. The previous service, metrics, timeline, deployment, and incident APIs are retained.

All three demos expose:

- `GET /health`
- `POST /admin/fail`
- `POST /admin/recover`
- `POST /admin/slow?delayMs=250` (optional parameter; configured default 2000ms)
- `POST /admin/normal`

Scripts:

- `scripts/register-demo-services.ps1`: explicit registration via the public API; repeated calls reuse the same IDs. Supports Docker DNS or direct-local targets. Conflicting existing targets are rejected without overwriting history.
- `scripts/validate-demo-lab.ps1`: bounded polling of scheduled health/incident transitions; normal Docker/API operations, direct SQL UUID snapshots, single-container stop/start, full volume-preserving restart, and runtime health/UID checks. Supports a WSL Docker engine and forwards Compose overrides. It never invokes manual LaunchGuard checks or deletes volumes.

Both scripts parsed successfully under Windows PowerShell. Bootstrap was run twice per validation pass with unchanged IDs. A deliberately conflicting `-Target Local` call was rejected, leaving the Docker registrations unchanged.

## Local port conflicts and reproduction

The workstation already had occupied ports 8080/8081 and 5433 (with host PostgreSQL also using 5432). Initial startup failed on those ports. An incomplete network attachment from the failed startup was cleared by recreating this project's containers with free ports, without deleting its volume.

Successful validation used host ports **9080–9083** and **15432**; Docker-internal ports remained 8080–8083 and 5432. The final full teardown/recreation completed cleanly with those overrides.

For the WSL-only Docker engine on this machine, restart the preserved lab from the repository using:

```powershell
wsl -d Ubuntu -- env POSTGRES_PORT=15432 LAUNCHGUARD_PORT=9080 PAYMENT_PORT=9081 ORDER_PORT=9082 NOTIFICATION_PORT=9083 docker compose up --build -d --wait --wait-timeout 180
.\scripts\register-demo-services.ps1 -BackendUrl http://localhost:9080
```

The above restores the normal 5s Compose monitoring interval. Use corresponding environment overrides in PowerShell when running `validate-demo-lab.ps1 -WslDistribution Ubuntu`, so its full restart retains those port settings; `.env` is another supported option. No personal `.env` was created or overwritten.

A preliminary Maven attempt failed before tests because PowerShell split an unquoted `-Dmaven.repo.local=...` argument. Quoting it resolved the invocation; the subsequent complete reactor and all tests passed. Early script validation also exposed Windows-backslash and empty-JSON-array handling differences in PowerShell 5.1; both were corrected and the final end-to-end script exited successfully with `result: PASS`.

## Limitations and scope

- Single-host local reliability lab, not production infrastructure.
- No authentication, frontend, external notifications, GitHub integration, Kafka, Redis, AWS, Kubernetes, rollback, or AI.
- Demo control state is volatile; notification-service simulates health only.
- Sequential monitoring means a slow service lengthens a pass and delays other observations.
- Thresholds remain global and checks are sampled rather than continuous.
- Trusted target URLs, no SSRF allowlist, no history retention/archival policy.
- Raw timeline responses remain unpaginated.
- Local database credentials and HTTP are development-only; host publications bind to loopback.
- Runtime image tags are maintained Java tags, not immutable digest pins.
- Automation requires PowerShell; Windows JVM tests need a reachable Docker engine, or Maven can run inside WSL alongside Docker.
- Initial builds require Maven/registry network access.
- Existing Testcontainers deprecated API and Mockito/Java agent warnings are non-fatal; no tests were skipped.
