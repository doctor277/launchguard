# V1.0 local validation — authentication and security hardening

Validated locally on 2026-10-05 and 2026-10-06 using Windows PowerShell, Ubuntu WSL, Docker Engine/Compose, Java 25.0.4.1, Node.js 24.21.0, Terraform 1.14.6, TFLint 0.64.0, and Playwright Chromium. No cloud resources were created, no images were published, and no commit, push, tag, or release was made.

## Scope and security decisions

- Added generic OIDC/OAuth 2.0 authentication. The browser uses Authorization Code with PKCE, while the backend validates Bearer JWT issuer, signature, expiry, audience, and mapped roles as a stateless resource server.
- Added a reproducible local Keycloak realm with `VIEWER`, `OPERATOR`, and `ADMIN` roles, a public SPA client, and a confidential automation client. Its accounts and credentials are explicitly local demonstration values.
- The access token and transient OIDC user/state data use tab-scoped `sessionStorage`, not `localStorage`; the application mirrors the active token in memory while attaching it to API requests. Tokens are not stored in LaunchGuard's database or written to logs.
- Server-side authorization is authoritative: `VIEWER` can read, `OPERATOR` can also trigger checks and register deployments, and `ADMIN` can also create and delete services. Health/readiness and the private Prometheus scrape endpoint remain anonymous; other routes deny by default.
- CSRF is disabled for the stateless Bearer-token API. CORS uses a configured origin allowlist without credentialed wildcard access. Production uses same-origin `/api` routing.
- Added bounded per-instance rate limiting for mutating operational routes, structured authentication/authorization errors, safe subject/role/action audit logs, and stricter validation of service targets and existing request fields.
- Added CSP, frame protection, content-type, referrer, permissions, and cache headers. HSTS is emitted only for HTTPS deployments; Terraform now rejects nonzero AWS application tasks without an ACM certificate.
- Preserved Flyway V1–V5 without adding a schema migration. LaunchGuard stores no users, passwords, access tokens, or refresh tokens.
- Hardened application containers with non-root users, read-only filesystems where compatible, dropped capabilities, `no-new-privileges`, and narrowly scoped temporary filesystems. Keycloak retains the writable paths required by its development runtime.

## Security review and repository checks

A diff-focused static security review covered all 48 changed source files. It initially identified one low-severity deployment configuration issue: authenticated AWS traffic could be enabled without TLS. The final tree remediates that issue by requiring an ACM certificate for nonzero application tasks, conditionally enabling HSTS only with HTTPS, rejecting non-loopback cleartext OIDC/reporting endpoints, and testing those safeguards. No reportable finding remained after remediation.

Two potential cleartext-transport candidates in operator scripts were reviewed as trusted endpoint configuration, then hardened anyway with the same HTTPS-except-loopback rule. A backend audit-log test additionally exposed that an authorization denial was being logged before Spring Security assigned the final response status; moving the audit filter before exception translation now records the true `403` and is covered by a test.

The final secret/path/attribution scan found no AWS keys, GitHub tokens, private keys, real OIDC secrets, personal filesystem paths, or internal-tool attribution in tracked release sources. `.env`, Terraform state, generated reports, `node_modules`, test output, and build directories remain ignored and untracked.

## Known boundaries

- Rate limiting is deliberately per application instance and is not a distributed quota system.
- The SPA uses a short-lived access token and interactive reauthentication; it does not persist or use refresh tokens.
- Local Keycloak uses demo credentials and HTTP on loopback only. It is not a production identity service and is not part of the AWS topology.
- Anonymous Prometheus access is intended for the private scrape path; network isolation is required outside the local lab.
- The AWS architecture is statically validated but has not been applied to an AWS account. Provider permissions, quotas, DNS, certificates, external identity-provider redirects, and live ECS/RDS/MSK behavior remain deployment-time validation items.
- Container CVE gating and Maven vulnerability gating were intentionally deferred. CodeQL, Dependabot, npm audit, pinned images/actions, ECR scan-on-push, and release SBOMs provide deterministic V1.0 coverage without introducing a noisy blocking scanner.
- LaunchGuard remains a single-tenant engineering/portfolio project, not a production monitoring or identity platform.

V1.0.0 is locally release-ready subject to hosted CI and an operator-approved release process. Nothing was committed, pushed, tagged, released, published, or deployed during this validation.
