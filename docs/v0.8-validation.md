## Scope and architectural decisions

- Artifacts are `0.8.0-SNAPSHOT`; controller/service/repository structure, Kafka DTOs, deployment correlation, incident logic, and Flyway V1-V5 remain intact.
- Backend and worker use Micrometer observations and the Spring Boot OpenTelemetry bridge. Prometheus scrapes metrics directly; applications send only traces through the Collector to Tempo. Starter-enabled OTLP metric/log exports are explicitly disabled.
- Native Spring Kafka observations propagate W3C context through request/result headers. A captured worker observation is reopened on the bounded executor thread; the outbound JDK HTTP sender injects W3C headers. IDs are trace attributes and log fields, never metric tags or persistent tracing columns.
- Business counters execute after transaction commit, only at newly persisted results/new incident openings/actual resolutions. Operational dispatch counters reflect successful broker ACKs; result processing timers also measure duplicates/retries/poison records.
- Open-incident/service gauges issue SQL counts. In-flight/worker-active/worker-queue gauges reuse existing process state. No history is loaded for these gauges; no migration/index change is required.
- Non-root apps, configurable loopback ports, existing PostgreSQL named volume, CI/reporting contracts and workflows are preserved.
- The Java coding and Docker skills guided constructor-injected telemetry, immutable existing event contracts, bounded metrics, pinned/non-root images and honest integration/runtime validation.

## Management and monitoring configuration

Only `health` and `prometheus` are exposed over HTTP; JMX endpoint exposure is disabled and health details are hidden. Backend readiness includes application state, PostgreSQL and Kafka. Worker readiness includes state/Kafka. Liveness is independent of those dependencies. Management endpoints share the existing app port.

Prometheus scrapes backend:8080 and probe-worker:8084 every 5s, with 24h retention in a named volume; no demo scrape or broker exporter is added. Collector OTLP HTTP/gRPC receivers feed memory limiting and batching, then the `otlp_grpc/tempo` exporter. Collector health is on 13133. Tempo is single-node with local WAL/blocks in a 1GiB tmpfs and 1h retention. Grafana provisioning supplies both datasources and the LaunchGuard Platform dashboard (16 signal panels across five section rows). No application frontend was built.

Pinned monitoring images (version + digest in Compose): Prometheus v3.10.0, Grafana 12.4.11, Collector contrib 0.147.0, Tempo 2.10.7. Their declared users are nobody, 472, 10001:10001, and 10001:10001 respectively.

Custom counters cover dispatches/failures, committed HEALTHY/DOWN results, ignored duplicate/deleted-service results, incident openings/resolutions, and worker HEALTHY/DOWN/ERROR outcomes. Histogram timers cover backend result processing and worker HTTP duration, with additional custom observation timers. See the README for exact names/semantics. Kafka records-produced/consumed/fetch-lag metrics are native Micrometer client binders, not custom business counters.

## Limitations and follow-up boundaries

- Local trusted lab only: loopback binding, anonymous Grafana Viewer, no application authentication/TLS/tenant isolation.
- Counters reset on restart and can undercount after a crash between database commit and metric update; history remains authoritative.
- Sampling/export queues are bounded; traces can be dropped when Collector/Tempo are unavailable. All traces are sampled in the demo, not a production recommendation.
- Tempo tmpfs traces disappear on stop/recreation and can fill before time retention. Grafana UI state is disposable; Prometheus's 24h named storage survives normal restarts.
- SQL gauges depend on database availability/existing connection timeouts; slow/unavailable PostgreSQL can delay scraping. In-flight counts follow the existing 5s expiry cleanup.
- Aggregate probe latency is intentionally not per-service Prometheus telemetry; use reliability history and trace/log identifiers for individual service investigation.
- This is an eight-service cardinality smoke check plus a 100-ID meter test, not a thousands-of-services capacity benchmark.
- No demo-server spans, per-SQL spans, log ingestion backend, custom broker platform, external alerts/notifications, rollback, AWS/Kubernetes, frontend or AI features.
- Hosted Actions/GHCR results require an independently authorized hosted run.
