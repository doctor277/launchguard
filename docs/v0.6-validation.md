# LaunchGuard V0.6 validation

Scope: V0.6 only — event-driven health monitoring. No future milestones or automatic commit.

## Architecture and changes

The seven-module Maven reactor (parent plus six child modules) is version `0.6.0-SNAPSHOT`. New `monitoring-events` owns explicit version-1 JSON contracts and shared Kafka topic/retry/health configuration. New `probe-worker` is a standalone Spring Boot application with no JDBC/JPA dependency, database credentials, or PostgreSQL network attachment.

Scheduled flow:

```text
backend scheduler → HealthCheckRequested → Kafka → probe-worker HTTP GET
                  → HealthCheckCompleted → Kafka → backend transaction → PostgreSQL
                                                     → existing incident evaluator
```

The synchronous manual check remains unchanged. New `POST /api/services/{id}/check/async` returns HTTP 202 with `requestId`, `serviceId`, and `status: QUEUED`; it does not await the probe. Immediate publication errors return structured 503, an existing in-flight async request returns 409, and unknown services return 404. Check-history DTOs now expose nullable `probeRequestId`.

Request fields: `eventVersion, requestId, serviceId, deploymentId?, targetUrl, requestedAt, timeoutMs`. Completion fields: `eventVersion, requestId, serviceId, deploymentId?, status, httpStatus?, responseTimeMs, errorMessage?, checkedAt`. Contracts are separate from JPA. The README contains full JSON examples and validation/nullable-field semantics.

Primary topics are `launchguard.health-check.requests` and `launchguard.health-check.results`; each has a matching `.dlt`. Applications create six partitions per topic, replication factor 1, with broker auto-creation disabled. All message keys are service UUID strings. Request routing explicitly separates the first six creation-order service ordinals, and results retain that partition. Affinity can change after registry deletion; there is no global ordering. Service row locks serialize persistence and older completion timestamps cannot regress current status or re-evaluate incidents.

Worker defaults: six consumers, four HTTP probe threads, bounded queue 64, eight records per poll. HTTP deadlines include body completion. 2xx is HEALTHY; other HTTP responses and network/timeout/DNS failures are valid DOWN observations. Worker offsets are acknowledged only after result publication succeeds; backend offsets follow committed persistence. Transient consumer errors receive two retries after the first attempt, 500ms apart; malformed/unsupported contracts are non-retryable and recovered to DLT. DLT publication failure prevents recovery/acknowledgement until publishing succeeds.

V4 adds nullable `health_checks.probe_request_id` and a concurrent unique partial index for non-null values. V1, V2, and V3 are unchanged. Flyway uses non-transactional script metadata plus session-level PostgreSQL advisory locking. Duplicate detection, insertion, current-status update, and the existing incident evaluator run within one transaction under a service row lock; duplicate records have no additional incident effect. Deleted-service results are ignored safely. Metrics SQL and existing bounded incident-history queries are preserved; dispatch adds a creation-order count query.

The Java, Docker, and database-migration skills guided framework-aligned code, non-root digest-pinned multi-stage images, health-gated startup, and the nullable/concurrent migration.

## Problems found and resolved during validation

- Initial test compilation exposed an incorrect MonitoringProperties constructor in a new test; corrected.
- Actual PostgreSQL showed concurrent index creation waiting on Flyway's transaction-level advisory lock. Session-level locking fixed it, matching [Flyway's PostgreSQL guidance](https://documentation.red-gate.com/flyway/reference/database-driver-reference/postgresql-database). The aborted run was not counted as a passing test run.
- PowerShell's `history` alias shadowed the new helper; renamed to `Get-KafkaHistory`.
- A pipe character in the Kafka replay delimiter was interpreted by WSL's command launcher; changed to a shell-safe colon, retaining UUID message keys and valid JSON.
- Closing the Spring test context manually during teardown caused Spring's after-class listener to fail even though test methods passed. Teardown now closes Kafka clients while leaving context lifecycle ownership with Spring.
- Broker health clients are disabled only in the original database-only test context; the dedicated real Kafka suite and production retain broker health checks. No important integration path was replaced with mocked Kafka or skipped.
- One intermediate lab run recreated applications after refreshed images; the final run explicitly used `--no-recreate` and asserted unchanged IDs, so that intermediate run was not used as reconnection evidence.

## Limitations and handoff

- One backend instance; in-memory guard and no durable scheduling/outbox/distributed lock.
- At-least-once requests can re-probe. Idempotent result persistence is not end-to-end exactly-once.
- 202 does not promise durable dispatch/completion. Failed/expired requests can miss observations; subsequent schedule passes recover monitoring.
- Six partitions/six consumers separate the first six registered services; more services can collide. Deletions can reroute partition affinity; no global ordering.
- Four saturated probe threads can delay fast work. No throughput/load/HA guarantee.
- Older results are persisted without regressing status or retroactively rebuilding incidents; equal timestamps can reflect arrival order.
- Sync manual probes retain a separate guard and can overlap async work.
- Kafka is one plaintext KRaft broker, replication factor 1, with image-provided anonymous volumes but no explicitly managed named broker storage. Restart retains state; down/up does not automatically reuse anonymous volumes, so Kafka persistence across recreation is not guaranteed. PostgreSQL history is persistent.
- No Kafka/database atomic transaction, job API, DLT replay UI, retention policy, authentication, SSRF allowlist, external notifications, or frontend.
- V4 is non-transactional; partial migration failure needs reviewed state-aware recovery. Reversals use a new migration, never edits to applied V1–V4.
- Demos and credentials remain deliberately local-development-only. Only V0.6 was implemented.

The lab is left running on the alternate ports above; controls were restored to healthy/normal. To stop it without deleting PostgreSQL history, run `wsl -d Ubuntu -- docker compose down` from this checkout. Do not add `-v`.
