# V0.7 validation — CI/CD and automatic deployment reporting

Validated locally on 2026-09-28. Only V0.7 was implemented. No commit, push, remote-repository change, hosted Actions run, or GHCR publication was performed.

## Scope and architecture

The existing REST/service/repository backend, Kafka contracts, database-free worker, three demos, metrics, and incident evaluator remain intact. All Maven artifacts advance to `0.7.0-SNAPSHOT`.

The deployment API gains optional `source` (`MANUAL`/`CI`), `environment`, `imageTag`, and `externalId`. Old JSON clients default to MANUAL. DTOs remain the HTTP boundary; current/incident summaries retain their compact V0.6 contracts. Deployment detail and paginated history expose the new metadata. Optional history filters were deliberately not added.

External IDs are case-sensitive and scoped to a service, allowing one CI run to report multiple services. A first report returns 201/Location; identical replay returns 200/Location and the original ID/timestamps. Version retains existing trimming; all other material fields compare exactly. Conflicts return structured 409 without modifying history/current state. Replaying an older deployment never reactivates it. Null IDs retain create-always behavior.

Registration acquires a short PostgreSQL `FOR NO KEY UPDATE` service-row lock before lookup/insert. This serializes concurrent reports without blocking foreign-key KEY SHARE locks from check inserts. The database unique index is the final safeguard. Native service-only lookup avoids locking an outer join's nullable current-deployment side. Registration timestamps use PostgreSQL microsecond precision so initial responses and persisted replays agree.

Java, Docker, migration, and GitHub-operation skill guidance influenced immutable DTOs, additive schema expansion, concurrent index creation, non-root images, and minimal workflow permissions. No architecture rewrite or future milestone functionality was introduced.

## V5 migration and preservation

V5 adds `source VARCHAR(16) NOT NULL DEFAULT 'MANUAL'`, nullable environment/image/external-ID fields, a two-source check constraint, and concurrent partial unique index `uk_deployments_service_external_id(service_id, external_id) WHERE external_id IS NOT NULL`. Its script metadata disables migration transactions; the existing session-level Flyway PostgreSQL advisory locking remains configured.

Before the live upgrade: 3 services, 6 deployments, 14,653 health checks, schema V4. V5 applied successfully against the existing named volume, without deleting data. Direct SQL confirmed V1–V5 successful, six legacy deployments now MANUAL with null optional metadata, and a valid unique partial index. Existing V1–V4 files have no Git diff. The migration test upgrades a V1 schema step-by-step through V5 and verifies legacy IDs, deployment/check relationships, latency, current deployment, and empty incident history remain intact.

This is forward-only and additive. Column/constraint operations still take a short schema lock. Concurrent-index migration failures can leave partial DDL/invalid indexes; recovery requires inspection and a reviewed forward plan, not automatic repair/drop/downgrade. Large production datasets were not tested.

## CI/delivery design

CI triggers on PRs/pushes to main and supports reusable calls. Ubuntu 24.04, Java 25, Maven Wrapper `clean verify`, Maven dependency caching, real Testcontainers, zero-skipped/missing-report gate, PowerShell contract/syntax checks, safe negative configuration gate, digest-pinned actionlint/ShellCheck, Compose config, and all five image builds. Reports upload even on failure. Same PR/branch obsolete CI runs cancel; timeout 40 minutes; permission contents:read; checkout credentials not persisted.

Delivery is workflow_dispatch, requires reusable CI success, and restricts delivery/publication to non-fork main. It starts a runner-local Compose lab, exercises actual deployment reporting and monitoring, saves metadata/evidence, optionally reports to a reachable external instance, optionally publishes GHCR images, and cleans up runner containers. It does not deploy to a remote host. Unset LAUNCHGUARD_URL produces an explicit external-reporting skip; the local demonstration still runs. Windows localhost is never assumed reachable from a hosted runner.

Only three GitHub actions are used, pinned to release commits: checkout v6.0.2, setup-java v5.2.0, upload-artifact v4.6.2. References were checked against the publishers' release commits: [checkout](https://github.com/actions/checkout/commit/de0fac2e4500dabe0009e67214ff5f5447ce83dd), [setup-java](https://github.com/actions/setup-java/commit/be666c2fcd27ec809703dec50e508c2fdc7f6654), [upload-artifact](https://github.com/actions/upload-artifact/commit/ea165f8d65b6e75b540449e92b4886f43607fa02). The [actionlint publisher documents the container validator](https://github.com/rhysd/actionlint/blob/main/docs/usage.md).

Optional GHCR uses built-in GITHUB_TOKEN through password-stdin, contents:read/packages:write only in delivery, and logout cleanup. No PAT/custom secret or PR publication. Tags are `sha-<full-SHA>` and `<application-version>-<full-SHA>` under `ghcr.io/<lowercase-owner>/launchguard-<app>`. No latest/bare-version tag is pushed. Tags identify commits but are not registry-enforced immutable objects; pin the registry digest for strict content immutability.

External report variables are LAUNCHGUARD_URL, LAUNCHGUARD_SERVICE_ID, and LAUNCHGUARD_ENVIRONMENT. They register metadata for an operator-managed deployment only. Authentication, publicly exposing the API, AWS/Kubernetes, rollback, external notifications, and full observability are outside scope.

## Limitations and hosted follow-up

Locally validated: complete builds/tests, actual PostgreSQL/Kafka containers, YAML/lint and PowerShell contract/syntax, all image builds/provenance/non-root execution, full Compose startup, CI reporting, health/incident correlation, replay/conflict, schema/index preservation, and whitespace checks.

Not executed: GitHub-hosted Actions, Maven cache/artifact upload on GitHub, GITHUB_TOKEN package permissions, external-instance reachability/reporting, or GHCR publishing. They need an explicitly authorized hosted run after commit/push. No publication or hosted execution success is claimed. Branch protection requiring CI is also an operator configuration, not changed here.

Other limitations remain: no authentication/authorization, frontend, cloud platform, automatic rollback, external notifications, AI, full telemetry stack, per-service policies, distributed scheduling, or history retention. SHA tags are not registry-enforced immutability; use digests. Service-scoped external IDs require distinct IDs for different environments of one service. The local history snapshot is intended for the small lab, not millions of production rows. V0.7 stops here.
